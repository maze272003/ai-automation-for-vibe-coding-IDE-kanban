# Workflow integrity: no silently stuck stories + readable agent terminal

Status: GLM SATISFIED (round 3, 2026-11-07; 0 blockers — rounds 1–2 findings all incorporated). Author: GLM 5.3 (Codex handoff per user instruction; Codex credits exhausted 2026-11-07).

## Developer need and evidence

The board's promise is that every story keeps moving — NEW → READY → IN_PROGRESS → TESTING → READY_FOR_REVIEW → AWAITING_MERGE → DONE — or lands visibly in BLOCKED for a human. Four silent-stall paths violate that today (traced in `apps/orchestrator/src/agents/runner.ts`):

- **S1 — terminal job failure can never be re-enqueued.** The discover idempotency keys (`implement_${storyId}_${statusVersion}` ~:304, `verify_${storyId}_${sha}[_${verificationId}]` ~:349/:370, `review_${storyId}_${sha}` ~:418, `rework_verify_${storyId}_${sha}_${attemptCount}` ~:384) collide with the failed job row forever (`JobQueue.enqueue` no-ops on conflict), and `handleImplementJob` fails the job without blocking when `implementStory` returns a pre-claim `ok:false` (dirty worktree, HEAD mismatch) or throws. For review, in-loop failures already end BLOCKED (reviewer.ts blockStory / finishReview error branch) — the unblocked paths are the pre-loop early returns and thrown exceptions; for verify, `handleVerifyJob` already blocks immediately on error (verify is NOT a silent stall today — see RE2).
- **S2 — missed post-evidence transitions stall silently.** A crash or guard failure between evidence write and transition leaves TESTING with a `passed` verification row (no `discoverVerification` branch) or READY_FOR_REVIEW with an existing reviews row (`discoverReview` skips on `existing`).
- **S3 — planning budget exhaustion parks invisibly.** `discoverPlanning` skips stories at `MAX_PLANNING_ATTEMPTS` (`failedPlans >= MAX` → `continue`), leaving them in NEW/`planning_failed` with no BLOCKED flag, no event, no board signal.
- **S4 — orphaned IN_PROGRESS runs.** No discoverer selects IN_PROGRESS. Three shapes: `activeRunId` null (crash between claim and setActiveRun), `activeRunId` → terminal run row (crash between failRun and blockStory), and — the most common — `activeRunId` → still-`running` run row with a dead job (any throw after `claim_implement`, e.g. git candidate capture or skills injection).

Separately, the agent-response terminal (`apps/ui/src/components/kanban/terminal-modal.tsx` ~:566–572) renders tool-event bodies as `JSON.stringify(state.input)` and text events in monospace — prose is not typeset as prose and tool calls are raw JSON noise. The user asked for a friendly, readable agent response view.

## Scope and requirements

- **RE0 — one scoped state-machine change.** `fail` becomes legal from NEW and READY as well as ACTIVE_STATUSES (`packages/workflow/src/machine.ts` `case 'fail'` stateGuard: `[...ACTIVE_STATUSES, 'NEW', 'READY']`). Rationale: a story that cannot plan or cannot start implementing is blocked, and `blockedFrom`/`recover` already model arbitrary sources (T14/T15 recover to READY/NEW; T16 resume only from RESUMABLE statuses, so a NEW/READY-blocked story recovers explicitly). No other guard, transition, or status semantics change.
- **RE1 — attempt-aware, round-scoped re-enqueue.** Stage keys become `<base>_<statusVersion>_r<n>` with bases `implement_<storyId>`, `rework_<storyId>_<sha>`, `verify_<storyId>_<sha>`, `review_<storyId>_<sha>`, where n = count of durable_jobs rows with status `failed`/`dead` whose idempotency key matches `<base>_<statusVersion>_r%`. The `_r` suffix is a fresh namespace (legacy keys cannot collide); `statusVersion` advances on every transition (recover, rework loops, candidate commits), so each stage round starts at n=0 — a human `recover()` resets the retry budget instead of colliding with it. `rework_verify_*` is replaced by the `rework_` base above (the old key collided because `attemptCount` alone never advances on retry).
- **RE2 — bounded auto-reprocess with honest terminal states.** Per stage round: enqueue while `n <= MAX_STAGE_JOB_RETRIES` (2), block when `n > MAX_STAGE_JOB_RETRIES`. That is exactly r0 (first attempt) + r1 + r2 re-enqueues, then a terminal action. Terminal actions: implement/rework stages → `fail` (environment) with detail naming stage, round counts, and the last `durable_jobs.lastError` (through the runner redactor); review stage → `fail` (reviewer_blocked) likewise; NEW planning budget exhaustion → `fail` (invalid_agent_output) naming the plan attempts (legal after RE0). Verify errors keep their current immediate-BLOCK behavior in `handleVerifyJob` (documented, unchanged); the queue's lease-expiry path (`sweepExpired`, maxAttempts=3) remains verify's retry mechanism.
- **RE3 — stuck-story sweep.** New module `apps/orchestrator/src/agents/stuck-stories.ts` exposes `sweepStuckStories(deps)`; `AgentRunner.tick()` runs it after the discoverers. It considers non-terminal, non-hold stories with **no queued/leased durable job for the story at all** (so it can never fight a live handler, including an expired-but-leased job) and:
  - NEW + `planning_failed` + plan budget exhausted → `fail` (invalid_agent_output);
  - READY/REWORK → attempt-aware implement re-enqueue, bounded by RE2;
  - TESTING: `passed` verification row for `candidateSha` → re-fire `verification_passed`; `failed`/`error` row → the existing rework path re-enqueue (attempt-aware `rework_` base); missing/`running` row → attempt-aware verify re-enqueue;
  - READY_FOR_REVIEW: review row for `candidateSha` with verdict APPROVED → re-fire `review_approved`; CHANGES_REQUESTED → re-fire `review_changes_requested`; BLOCKED verdict rows already block via finishReview — no row → attempt-aware review re-enqueue;
  - IN_PROGRESS with no queued/leased job → the run is orphaned: if the `agent_runs` row is still `running`, mark it `interrupted` (direct update + `emitRunFinished`, the established implementer/reviewer pattern), then `fail` (interrupted) naming the run id and its prior status; same for a terminal run row; `activeRunId` null → `fail` (environment, "run lost before it started");
  - AWAITING_MERGE is exempt (waits for human approval by design); BLOCKED/DONE/CANCELLED match no branch.
  All transitions go through `WorkflowService`. Re-fire guard-failure handling: a failed `attempts` guard → `fail` (retry_limit) immediately (legal from READY_FOR_REVIEW); any other re-fire guard failure → one informational storyEvents row and an in-memory per-process skip-set (a process restart allows exactly one more attempt — bounded, no per-tick spam).
- **RE4 — visible auto-reprocessing.** Every retry-tier re-enqueue (ordinal r ≥ 1, discoverer or sweep) writes one informational storyEvents row (`type: 'internal_error'`, payload `{ message: 'stage re-queued by integrity sweep'|'stage retried', stage, ordinal }`, redacted). Terminal blocking actions land as ordinary workflow transitions with honest details. r0 first attempts stay silent (normal operation).
- **RE5 — readable agent terminal (UI-only).** Terminal-tab events render as: friendly tool names (Read/Edit/Write/Bash/Grep/…) with a one-line summary (file path or command) and a status chip (running/completed/failed) plus duration when known; assistant and user text as proportional-font prose (`whitespace-pre-wrap`; monospace only for tool/code payloads — today even text renders in mono); reasoning blocks dimmed and collapsed past a threshold with an expand control; raw tool input behind a "Show raw JSON" toggle; long text clamped with expand. No route/API contract changes; existing `data-testid`s and keyboard behavior unchanged (no testids exist inside the event rendering today).

## Acceptance and limits

New/extended tests (temp-db helpers, fake clocks, no real repositories, no CLI spawns): failed implement job → re-enqueued next tick under `_r1`; two retries (`_r1`,`_r2`) then BLOCKED with stage detail (predicate `n > 2` pinned); recover() bumps statusVersion → round resets to r0 (no ping-pong); rework key collision fixed (`rework_` base advances on statusVersion); sweep golden scenarios: S2 re-fires (TESTING+passed → READY_FOR_REVIEW; READY_FOR_REVIEW+APPROVED → AWAITING_MERGE; CHANGES_REQUESTED with exhausted attempts → BLOCKED(retry_limit)), S3 planning budget → BLOCKED(invalid_agent_output), S4 all three IN_PROGRESS shapes (incl. running-run marked interrupted + run.finished emitted), exemptions (AWAITING_MERGE, hold, queued/leased job present); machine: `fail` now legal from NEW/READY, still illegal from DONE/CANCELLED, blockedFrom recorded; RE4 storyEvents rows on r≥1 enqueues only. Existing suites stay green (runner, workflow, stories, planner, implementer, reviewer). UI verified by typecheck + build only.

Non-goals: no state-machine changes beyond the single RE0 guard extension; no new statuses; no run.output wiring; no Phase 6 agent-team contracts (separate failing baseline); no live CLI execution; no `handleVerifyJob` behavior change.
